# 🏦 B2B Финтех-Платформа: Монорепозиторий учета и документооборота

## 🚀 Реализованный бизнес-функционал
### 1. Графическая валидация данных
* **Динамический контроль ввода (UX/UI Validation):**
  * Непрерывная валидация реквизитов (ИНН, КПП, даты) «на лету» непосредственно в интерфейсе пользователя `[Client]`.
  * Интерактивная подсветка ошибочных полей с мгновенной блокировкой отправки форм (ввод некорректных данных в систему невозможен до полного исправления или заполнения обязательных полей) `[Client]`.

### 2. Сервис регистрации и авторизации
* **Поэтапный процесс регистрации нового предприятия (Data Flow):**
  * Сбор данных пользователя и предприятия для составления единого бизнес-профиля. `[Client]`
  * Формирование печатной формы заявления о регистрации для ознакомления и структурированного JSON-файла для последующего заверения. `[Client]`
  * Прием отсоединенной электронной цифровой подписи (ЭЦП) пользователя, наложенной на файл JSON. `[Server]`
  * Валидация подписи, извлечение данных из открытого ключа ЭЦП и кросс-проверка с данными исходного JSON. `[Server]`
  * Криптографическое хэширование пароля с использованием алгоритма Argon2. `[Server]`
  * Атомарное создание записей о новом пользователе и предприятии в СУБД PostgreSQL. `[Server]`
  * Генерация авторизационной сессии и формирование защищенной связки `Token — DeviceId`. `[Server]`
* **Авторизация и восстановление доступа:**
  * Быстрый вход по валидному сессионному токену, сохраненному в защищенном системном хранилище устройства. `[Client / Server]`
  * Аутентификация по строгой B2B-связке (ИНН физлица, ИНН предприятия, КПП предприятия) и паролю. `[Client / Server]`
  * Сервис двухфакторного восстановления доступа через Flash Call (авторизация по коду из входящего звонка). `[Client / Server]`

### 3. Сервис машиночитаемых доверенностей (МЧД)
* Графический и программный интерфейс для гибкого управления правами доступа пользователей. `[Client / Server]`
* Доступны полномочия для ЭДО с ФНС РФ и B2B ЭДО из официального списка полномочий, утвержденных ФНС РФ. `[Client / Server]`
* Поддержка кастомных полномочий для гибкой настройки прав доступа внутри самого приложения. `[Client / Server]`
* **Формирование новой доверенности:**
  * Сбор данных доверителя, доверенного, реквизитов доверенности и выбранных полномочий `[Client]`.
  * Автоматическая генерация МЧД актуального XML-формата, утвержденного ФНС РФ `[Client]`.
  * Прием отсоединенной электронной подписи руководителя предприятия на файле XML `[Client]`.
  * Извлечение данных из открытого ключа ЭЦП руководителя предприятия, валидация данных владельца подписи и данных XML. `[Server]`
  * Надежное сохранение доверенности в хранилище на сервере. `[Server]`
* Модуль контроля доступа, динамически проверяющий полномочия пользователя по базе данных актуальных МЧД при выполнении операций. `[Server]`
* Графический интерфейс для наглядного просмотра текущих актуальных прав доступа пользователя. `[Client]`

### 4. Сервис бухгалтерского учета и налоговой отчетности (РСБУ core)
* **Ядро двойной записи в реальном времени:**
  * Реализация классического механизма двойной записи для строгого отражения хозяйственных операций на счетах Российского плана счетов бухгалтерского учета (РСБУ).
  * Поддержка активных и пассивных счетов.
* **Автоматизация и ввод первичных данных:**
  * Модуль ручного ввода и корректировки сложных бухгалтерских проводок через графический интерфейс. `[Client]`
  * Интеллектуальный парсинг банковских выписок: автоматическое распознавание транзакций, генерация проектов проводок и их последующая верификация/корректировка пользователем перед фиксацией в главной книге. `[Client]`
* **Генерация и валидация регламентированной отчетности:**
  * Формирование официальных налоговых деклараций и Уведомлений об исчисленных суммах налогов в двух стандартах: `[Client]`
    * **PDF-формат** — генерация печатных форм, строго соответствующих актуальным машиночитаемым бланкам ФНС РФ для бумажного документооборота. `[Client]`
    * **XML-формат** — выгрузка валидных файлов электронного документооборота, готовых к отправке в налоговые органы через операторов ТКС. `[Client]`



## 🛠 Технологический стек и ключевые библиотеки
Проект разработан на базе современного асинхронного стека **Rust (Workspace)**.
* **Ядро клиента:** **Tauri (v2.10)** — легковесный фреймворк для сборки нативных приложений под PC и мобильные платформы / TypeScript.
* **Ядро сервера:** **Axum (v0.7)** — высокопроизводительный асинхронный веб-фреймворк для реализации REST API бэкенда (`back_api`).
* **Кастомная библиотека `shared_lib`:** Синхронизация общих кастомных структур данных.
  * **TS-RS:** Автоматическая генерация TypeScript-интерфейсов из Rust-структур на этапе компиляции, обеспечивающая полную типобезопасность на фронтенде.
* **Асинхронный runtime:** **Tokio & Futures** — среда выполнения для эффективной обработки конкурентных асинхронных задач.

### 🔹 Криптография и безопасность
* **Argon2 & Password-Hash:** Современный криптостойкий алгоритм хэширования для безопасного хранения паролей пользователей.
* **Blake3:** Сверхбыстрая криптографическая хэш-функция для контроля целостности файлов документов.
* **Keyring:** Безопасный интерфейс для взаимодействия с системными хранилищами паролей ОС (Secret Service / Keychain) на стороне клиентов.
* **Machine-UID:** Извлечение уникального идентификатора оборудования для валидации связки `Token — DeviceId`.
### 🔹 Контейнеризация и Инфраструктура (Docker)
Для локального развертывания и изоляции сервисов используются **два Docker-контейнера**, оркеструемые через Docker Compose:
* **Контейнер СУБД PostgreSQL:** Хранилище основных данных системы, включая профили предприятий, сессии, проводки РСБУ.
* **Контейнер Криптосервиса (`crypto_service`):** Изолированная среда для выполнения чувствительных криптографических операций и валидации ЭЦП, защищающая основное приложение от прямых инфраструктурных рисков.
### 🔹 Специфические типы данных
* **Rust_Decimal:** Высокоточные финансовые расчеты в ядре бухучета (без погрешностей float-типов).
* **Chrono:** Работа с датами, временем и часовыми поясами (критично для МЧД и периодов проводок).
* **Uuid:** Генерация уникальных идентификаторов сущностей.
* **Vec1:** Гарантия наличия как минимум одного элемента в коллекциях на уровне системы типов.
### 🔹 Базы данных
* **SQLx:** Асинхронный драйвер с compile-time проверкой SQL-запросов и встроенным механизмом миграций (PostgreSQL для бэкенда и SQLite для локального кэша клиентов).
### 🔹 Мониторинг, Логирование и Утилиты
* **Tracing (Appender, Subscriber):** Структурированное асинхронное логирование работы микросервисов с поддержкой ротации файлов.
* **Tower-Http:** для Axum (логирование запросов, трассировка, валидация заголовков).
* **Tauri Plugins (v2):** Официальные плагины экосистемы Tauri для безопасного доступа к ресурсам ОС (`dialog`, `shell`, `fs`, `log`).


## 🧩 Описание архитектурных блоков (Crates)
### 📦 `shared_lib`
Центральный компонент монорепозитория, обеспечивающий сквозную типобезопасность, переиспользование бизнес-логики и единые стандарты обработки данных между сервером и кроссплатформенными клиентами.
Внутренняя структура модуля:
* **`client` (Клиентская бизнес-логика):** 
  * Содержит универсальный набор функций и хелперов, неизменных для разных клиентских платформ (PC и Mobile) и разных организационно-правовых форм предприятий.
  * Изолирована от сборки внутри серверного крейта `back_api`.
* **`err_models` (Единая подсистема обработки ошибок):**
  * Интеграция со слоями логирования `tracing`, `log` для серверной  и клиентской частей соответственно.
  * Обеспечивает лаконичность кода и детальное логировние причин сбоев.
* **`primitives` (Доменно-специфичные типы / Value Objects):**
  * Кастомные типы-обёртки над базовыми структурами со встроенной сквозной валидацией данных (ИНН, КПП, СНИЛС).
  * Интеграция и бесшовный маппинг в СУБД PostgreSQL (сервер) и в SQLite (клиент) обеспечивают корректность и целостность данных, в том числе в таблицах.
* **`sql_models` (Data Mapping слой):**
  * Структуры-зеркала, в точности отражающие схемы реляционных таблиц баз данных. 
  * Содержат вспомогательные структуры данных необходимые в разных частях функционала
* **`static_data` (Реестр форматов и шаблонов):**
  * Текстовые шаблоны, схемы и метаданные, необходимые для парсинга документов и построения мостов к жестким XML-структурам МЧД Федеральной налоговой службы (ФНС РФ).
* **`service` (DTO и Сетевые контракты):**
  * Структуры данных (Data Transfer Objects), описывающие взаимодействие частей программы и сгруппированные по функциональным модулям.
  * Единый реестр API-роутов, который гарантирует строгую синхронизацию адресов запросов со стороны клиентов и их корректный прием по ключам-маршрутам на стороне Axum-сервера.

### 📦 `back_api` (Серверная часть)
Сервис для хранения, доступа и синхронизации глобальных данных: компании, физлица, пользователи, подключения, договоры, бухгалтерские проводки. Центральный компонент — Docker-контейнер с СУБД PostgreSQL.
Внутренняя структура модуля:
* **`migrations`:** SQL-файлы для автоматического развертывания и обновления структуры таблиц в базе данных при старте сервера.
* **`handlers`:** Список обработчиков (хэндлеров) сетевых запросов, структурированных по функционалу. Принимают и отдают данные в формате JSON.
* **`parser`:** Модуль для обращения к внешним API (используется для автоматического заполнения реквизитов компаний через сервис **DaData.ru**).
* **`service`:** Основная логика сервиса — обработка запросов клиента и формирование ответных структур данных. Структура отражает функционал (авторизация, создание МЧД и прочее).
* **`sql_queries`:** Функции для отправки запросов в базу данных, аккуратно разложенные по именам таблиц.

### 🔐 `crypto_service` (Криптографический микросервис)
Изолированный сервис, который находится на том же физическом сервере, что и бэкенд, что обеспечивает между ними максимальную скорость обмена данными. Единственная задача сервиса — принимать файл электронной подписи, извлекать из него данные владельца (ФИО, СНИЛС) и проверять их подлинность. Центральный компонент — Docker-контейнер с установленной системой КриптоПро CSP.
**Цель выделения в отдельный сервис:**
* **Чистота окружения:** Для работы КриптоПро требуются специфические системные зависимости и установка корневых сертификатов Минцифры РФ (`russian_trusted_root_ca.cer`).
* **Стабильность и безопасность:** Сбой при проверке подписи или падение утилиты КриптоПро никак не затронут работу основного сервера приложений.
**Ключевые компоненты крейта:**
* `src/person_snils/` — логика извлечения и валидации данных из сертификата открытого ключа ЭЦП.
* `DockerFile` + дистрибутив КриптоПро (`linux-amd64_deb.tgz`) — автоматическая сборка изолированного крипто-окружения.

### 💻📱 `lite_pc` & `lite_mobile` (Клиентские приложения)
Ядро **Tauri (Rust)** + **Svelte 5 (TypeScript / Vite)**. Два отдельных крейта описывают интерфейс (HTML и CSS) под экраны компьютеров и мобильных телефонов. Остальная логика общая.
**1. Нативная часть (Rust / `src-tauri`):**
* **`commands`:** Список функций (команд), которые фронтенд вызывает из UI. Специфичные запросы обрабатываются в текущем крейте, универсальные (для разных форм собственности) — функциями `shared_lib`.
* **`service`:** Внутренние службы приложения (авторизация, локальное хранение данных в SQLite, проверка ключей устройства), сгруппированные по функционалу.
**2. Визуальная часть (TypeScript / `ui/src`):**
* **`models/` (`.svelte.ts`):** Глобальный менеджер состояния приложения и менеджеры отдельных микросервисов на базе Svelte 5. Также здесь находятся автоматически сгенерированные TypeScript-биндинги структур данных из `shared_lib`.
* **`service/` (`.svelte`):** Набор визуальных компонентов и интерфейсов, разложенных строго по бизнес-задачам: формы авторизации, конструктор МЧД ФНС, журналы бухгалтерских проводок и панели выгрузки налоговых отчетов.
* **`routes/`:** Стандартная файловая маршрутизация (точки входа `+layout` и `+page`). На практике используется только файл `+layout`, который динамически рендерит нужные модули и сервисы из папки `service`.
* **`style/`:** Модульные CSS-стили, вынесенные в отдельные файлы для каждого графического элемента (кнопки, инпуты, диалоговые окна) для простоты кастомизации UI.


## 🏛 Ключевые архитектурные решения
### 1. Управление состояниями через конечные автоматы (Rust Enums)
* **Единый паттерн состояний:** Для каждого функционального сервиса определена центральная структура данных на основе `enum` (например, `AuthStep`). Каждый элемент описывает конкретный шаг бизнес-логики: `Loading`, `RegisterStep1`, `RegisterStep2`, `Success`, `TryLater`. 
* **Строгий и предсказуемый Data Flow:** Клиент нажимает кнопку «Отправить» и получает структуру данных с результатом обработки, необходимую для следующего шага, либо `TryLater` в случае неудачи. Такой подход позволяет связать всю цепочку приложения *(Экран → Клиентское устройство → Сервер)* единым жестким форматом обмена данными. Компилятор гарантирует, что интерфейс не может оказаться в неопределенном состоянии. Все потенциальные ошибки в корневых функциях штатно обрабатываются системой, переводя приложение в безопасный и понятный для пользователя режим ожидания (`TryLater`), а библиотека `ts-rs` обеспечивает бесшовную обработку результатов любых сценариев на стороне фронтенда Svelte 5.

### 2. Сквозная совместимость и безопасность рефакторинга
* **Централизованные зависимости:** Все библиотеки и их версии прописаны один раз в корневом `Cargo.toml`. Модули (крейты) лишь импортируют их при необходимости. Это гарантирует сквозную совместимость библиотек во всем проекте, исключает конфликты версий и сквозную проверку кода компилятором.
* **Единый источник правды:** Описание кастомных структур данных происходит исключительно внутри библиотеки `shared_lib`. Это позволяет безопасно менять и рефакторить код: изменения в одном месте сразу применяются ко всей системе.
* **Автоматическая синхронизация типов:** Использование библиотеки `ts-rs` для генерации TypeScript-интерфейсов из Rust-структур гарантирует совместимость данных TypeScript и Rust.

### 3. Архитектура доступов на базе МЧД (Концепция Zero-Trust)
* **Динамические полномочия:** В системе полностью отсутствуют изначальные жесткие роли для пользователей (вроде «админ» или «бухгалтер») внутри учетной записи. 
* **Соответствие стандартам ФНС:** Пользователь авторизуется как физическое лицо по своей личной ЭЦП, права доступа вычисляются динамически на основе загруженных и подписанных руководителем XML-файлов машиночитаемых доверенностей (МЧД).

### 4. Архитектурные решения для фронтенда (Svelte 5)
* **Единая точка входа:** Стандартный файловый роутер SvelteKit используется только в одном месте (`+layout.svelte`), а все остальные интерфейсы (сервисы) рендерятся динамически как компоненты. Это убирает фризы и минимизирует потребление оперативной памяти устройством.
* **Разделение менеджеров состояния:** Архитектура построена на базе Глобального менеджера и изолированных менеджеров конкретных микросервисов. Глобальный менеджер переключает внутренние реактивные переменные, определяя, какой сервис нужно отобразить в данный момент. Это обеспечивает строгую изоляцию данных и исключает появление циклических связей в реактивных переменных Svelte.
